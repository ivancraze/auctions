# Использование AI

AI использовался как вспомогательный инструмент для анализа задания, проверки полноты OpenAPI-интеграции, поиска edge cases, подготовки черновых вариантов тестов и ревью результатов автоматических проверок.

## Какие части выполнялись с помощью AI

- декомпозиция требований на последовательные этапы;
- сверка реализованных сценариев с OpenAPI-контрактом;
- подготовка части однотипных fixtures, MSW-сценариев и тестовых случаев;
- реализация runtime-валидации ответов, обработки ошибок и документации по сформулированным кандидатом требованиям;
- проверка доступности, границ FSD, сложности компонентов и пользовательских сценариев;
- анализ результатов TypeScript, ESLint, Vitest и production build.

Кандидат самостоятельно формулировал требования, выбирал варианты и принимал либо отклонял результат после каждого этапа. AI помогал с реализацией, поиском edge cases, подготовкой черновиков и запуском проверок. Ответственность за итоговую архитектуру, выбранные компромиссы и работоспособность проекта остаётся у кандидата.

## Инициативы и решения кандидата

Ниже перечислены значимые предложения кандидата, сгруппированные по назначению, а не по хронологии работы.

### API и надёжность

- считать OpenAPI-контракт неизменяемым источником истины и не адаптировать его под интерфейс;
- генерировать TypeScript-типы и Zod-схемы из OpenAPI, а не поддерживать их вручную;
- проверять успешные ответы и problem responses backend через Zod `safeParse`, не ограничиваясь статическими TypeScript-типами;
- обрабатывать validation error `422` у формы ставки;
- добавить глобальный классовый Error Boundary для ошибок React-дерева;
- сделать MSW stateful, чтобы POST ставки изменял список, детали и историю ставок;
- оставить TanStack Query источником server state, а Zustand применять только для toast-уведомлений.

### Архитектура и качество кода

- использовать Feature-Sliced Design с публичными API slices и сегментов;
- перейти на короткие межслойные импорты через алиас `@/*` и barrel-файлы вместо длинных относительных путей;
- сортировать импорты группами: внешние библиотеки, внутренние модули проекта, затем стили;
- проверять архитектурные границы FSD с помощью Steiger и документировать только необходимые исключения;
- заменить общий `index.css` на `global.scss`, а стили компонентов хранить рядом с ними в SCSS Modules;
- декомпозировать крупные страницы и вынести самостоятельные `DetailSkeleton`, `AuctionsSkeleton`, `AuctionsLoader`, секции, поля фильтров и хуки;
- заменить длинные условия в JSX на именованные состояния и более простую композицию;
- добавить `AGENTS.md` с минимальными рабочими правилами и разделением ответственности между логикой, интерфейсом, тестами и ревью.

### Тестирование и mock-данные

- добавить минимальные тесты чистой логики: search params, request builder, ViewModel-мапперы и validation schema ставки;
- покрыть бизнес-сценарий ставки: валидацию, успешную mutation, backend-ошибку и success/error toast;
- проверять, что mutation обновляет в MSW-store текущую и доступную цену, статус пользователя и список ставок;
- снабдить тестовые сценарии JSDoc-описаниями;
- добавить отчёт покрытия Vitest в терминале и минимальные coverage thresholds;
- расширить fixtures до 35 аукционов с разными статусами, типами, ограничениями и доступностью действий;
- добавить небольшую development-задержку ответа списка, чтобы loader можно было увидеть и проверить вручную.

### UX и доступность

- показывать loader вместо карточек при применении и сбросе фильтров, опираясь на статусы TanStack Query;
- сделать действия фильтра доступными при прокрутке и последовательно доработать поведение панели без вложенного неестественного scroll-контейнера;
- синхронизировать фильтры с URL и сохранять отфильтрованную выдачу после перехода на аукцион и возврата к списку;
- выводить по 6 карточек на страницу;
- добавить явное действие открытия аукциона вместо неочевидного перехода только по маршруту карточки;
- добавить возврат к списку со страницы скрытой истории ставок;
- показывать хлебные крошки как на главной, так и на внутренних страницах;
- проверить доступность интерфейса, включая focus management, skip-link, семантику диалогов, подписи элементов и reduced motion;
- выровнять шапку по основному layout-контейнеру и оформить собственную стрелку `select` с нормальными отступами;
- добавить favicon с графикой аукционного молотка.

### Инструменты и воспроизводимость

- зафиксировать Node.js 26.5+, npm 11.17+ и Orval 8.23;
- добавить Brotli-сжатие production-ресурсов в Vite;
- настроить ESLint и Prettier для единообразной сортировки импортов;
- подключить Husky: lint, форматирование, Steiger и тесты перед commit, typecheck и тесты перед push;
- проверить чистоту Git-истории и не оставлять в поставке исходное PDF и служебные инструкции задания.

### Проверенные и отменённые варианты

- вариант отдельного состояния кнопки «Ставки скрыты» был реализован без изменения OpenAPI, оценён визуально и отменён кандидатом;
- вариант общего крупного заголовка «Аукционы» в layout был проверен и удалён, поскольку вызывал лишнее смещение интерфейса;
- несколько вариантов sticky-поведения фильтров были последовательно заменены после проверки на реальной высоте экрана.

## Какие предложения AI были отклонены

- подключение компонентной библиотеки: для объёма задания достаточно небольшого собственного UI-слоя;
- перенос всего состояния форм и фильтров в глобальный store: это дублировало бы React Hook Form, URL и TanStack Query;
- добавление отдельного mock-backend: MSW уже покрывает требуемую сетевую границу;
- создание общего barrel-файла для всего `src` и дополнительных абстракций без реальных потребителей.

## Что проверялось особенно внимательно

- nullable-поля, enum-значения и формы ошибок OpenAPI;
- генерация и runtime-проверка как успешных ответов, так и problem responses;
- ограничения `can_set_bet`, `hide_bets_history`, `hide_points_address_and_contacts` и `no_view_cargo_price`;
- соответствие цены ограничениям `min`, `max` и `step`;
- обновление MSW-store и инвалидация всех связанных query после ставки;
- безопасные fallback-значения для некорректных search params;
- loading, empty, error и unavailable states;
- доступность форм, фильтров, навигации, таблиц, уведомлений и управления фокусом;
- соблюдение публичных API и направлений зависимостей FSD через Steiger;
- отсутствие подтверждённых проблем с лишними ререндерами и чрезмерно крупными компонентами.

## Оставшиеся риски

- нет browser E2E-набора и автоматической визуальной проверки адаптивности;
- mock-словарь городов и объём fixtures меньше реального production-набора;
- production-интеграция с настоящим backend, авторизацией и инфраструктурой не проверялась;

## Что можно улучшить ещё за один день

- добавить Playwright-сценарии для desktop/mobile и accessibility-проверку;
- проверить приложение против тестового backend, если он доступен;
- добавить виртуализацию или более детальную оценку производительности на большом списке;
- расширить fixtures редкими комбинациями nullable-полей и торговых статусов;
- вынести визуальные токены в небольшой документированный design-system слой;
- либо переделать на AntDesign/Material UI.
